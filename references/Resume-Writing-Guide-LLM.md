# Resume Writing Guide for LLMs

> 用于指导大模型基于用户的**真实经历**撰写高匹配、高信息密度、结果导向、可验证、可面试追问的简历。
> 本 Guide 聚焦**简历写作本身**，不覆盖投递时间、薪资沟通、面试技巧等外围事项。

---

## 1. 任务目标

简历不是自传，而是针对目标岗位的证据页。模型的任务是完成：

```text
JD/目标岗位
→ 提取岗位能力与关键词
→ 从真实经历中筛选证据
→ 重构为“场景/问题—个人动作/判断—结果”
→ 按相关性排序
→ 压缩为可扫描表达
→ 做真实性与可追问性审计
```

最终让招聘方快速回答三个问题：

1. **匹配吗？**
2. **有证据吗？**
3. **值得面试吗？**

决策优先级：

```text
真实性 > 岗位匹配 > 证据强度 > 个人贡献 > 结果影响 > 可扫描性 > 文辞漂亮
```

## 2. 硬约束

### 2.1 不得编造

**MUST**

- 仅使用用户提供、材料明确支持或用户确认的事实。
- 不虚构公司、项目、职责、技术栈、论文、奖项、排名、用户量、收入、准确率、效率提升等。
- 不把“参与”自动升级成“主导 / Owner / 独立负责”。
- 不把团队成果自动写成个人成果。
- 不把“了解/用过”自动写成“熟练/精通”。
- 不为量化而编数字。

**MAY**

- 重组真实经历，使职责、方法、结果更清楚。
- 使用更贴近目标岗位的专业语言表达同一事实。
- 对缺失信息使用 `[补充X]` 占位，而不是补造事实。

**包装 = 把真实经历讲清楚，不是把 0 写成 100。**

### 2.2 所有强表述都要可举证

使用以下词语前检查证据：

`主导 / Owner / 独立负责 / 搭建 / 设计 / 重构 / 优化 / 显著提升 / 核心 / 端到端 / 精通`

使用任何数字前检查：

```text
数字如何计算？
基线是什么？
与候选人的动作有什么关系？
用户能否在面试中解释？
```

不能解释则降级措辞或删除。

### 2.3 匹配度优先于完整度

信息优先级：

```text
岗位强相关 + 有结果
> 岗位强相关 + 有明确动作
> 可迁移能力强
> 能证明学习/长期投入的信号
> 弱相关经历
> 填充信息
```

如果删除某项不会降低岗位匹配、可信度或差异化，优先删或压缩。

## 3. 标准工作流

### Step 1：识别目标

确定：

- 目标岗位 / JD
- 校招 / 社招 / 转行 / 复试等场景
- 中文 / 英文
- 现有简历还是从零写
- 页面限制

若信息不足，不得幻觉补全。优先继续处理已有信息；必要时只追问高价值缺口：

1. 目标岗位是什么？
2. 这段经历你本人具体做了什么？
3. 有哪些结果、规模、上线、采用、排名或可展示产物？

### Step 2：拆 JD

将 JD 拆成：

1. 核心任务
2. 硬技能/工具
3. 业务能力
4. 场景/行业经验
5. 软能力
6. ATS/HR 关键词

### Step 3：建立 JD—证据映射

内部按如下逻辑判断：

| JD 要求 | 用户证据 | 强度 | 动作 |
|---|---|---:|---|
| 有真实业务结果 | 实习/生产项目 | 强 | 核心展示 |
| 有明确项目动作 | 课程/个人项目 | 中 | 可展示 |
| 只学过/了解 | 课程/自学 | 弱 | 谨慎展示 |
| 无证据 | 无 | 0 | 不写 |

### Step 4：建立经历证据库

每段经历提取：

```text
场景 / 目标
问题 / 难点
个人角色与责任边界
关键动作
方法 / 工具
判断 / 取舍
结果 / 影响
规模 / 指标
可验证产物
```

### Step 5：选择与排序

企业求职默认：

```text
相关工作/实习
> 高质量项目/科研
> 开源/作品/竞赛
> 相关校园经历
> 技能/证书
```

同模块通常倒序，但整体排序服从**岗位相关性**。不得伪造时间关系。

### Step 6：重写核心 bullet

默认结构：

```text
场景/问题 → 个人动作/判断 → 结果/影响
```

### Step 7：植入关键词

只使用用户真实具备且与 JD 重要相关的关键词。优先把关键词写进**有证据的经历句**，而不是只堆在技能栏。

### Step 8：压缩

删除低价值内容 > 合并重复内容 > 精简措辞 > 最后才调整字号和间距。

### Step 9：真实性与可追问性审计

逐条检查：

```text
事实真实吗？
角色夸大了吗？
数字可解释吗？
技术真的用过吗？
结果能合理归因吗？
用户能否围绕重点 bullet 讲 2–3 分钟？
```

## 4. Bullet 写作规则

### 4.1 默认公式

```text
[场景/问题] + [个人职责/判断] + [关键动作/方法] + [结果/影响]
```

模板：

```text
• [能力/任务标签]：在 [场景] 下，针对 [问题]，负责 [个人范围]；通过 [方法/判断] 完成 [关键动作]，最终 [结果/影响/产物]。
```

不要机械补齐完整 STAR。简历只保留理解这件事所需的最短逻辑链。

### 4.2 按岗位选择结构

**业务/产品/运营/数据：**

```text
场景 → 信息/分析 → 判断 → 动作 → 结果
```

**技术/工程：**

```text
问题 → 方案 → 关键机制/取舍 → 指标/上线结果
```

**科研：**

```text
研究问题 → 方法 → 个人贡献 → 发现/产出
```

### 4.3 Ownership 动词必须符合事实

责任层级：

```text
支持/协助 < 参与 < 负责 < 独立负责 < 主导 < Owner
```

不要为了“更强”无依据升级。

技术动词可选：`设计 / 实现 / 搭建 / 重构 / 优化 / 部署 / 排查 / 验证 / 评估`

业务动词可选：`拆解 / 分析 / 识别 / 定义 / 制定 / 推动 / 协调 / 复盘 / 落地`

## 5. 结果与量化

优先寻找：

1. **业务指标**：收入、转化、留存、成本、满意度等
2. **技术指标**：延迟、吞吐、准确率、召回率、故障率等
3. **效率指标**：耗时、人力、自动化比例
4. **规模**：用户、样本、SKU、数据、区域、项目数
5. **质量/交付**：上线、验收、稳定运行、缺陷、成功率
6. **外部验证**：获奖、论文、专利、开源合并、排名
7. **决策影响**：推动策略、产品、流程变化
8. **可验证产物**：报告、看板、代码、模型、数据集、文档

### 5.1 没有数字时

不要编数字。用真实的：

- 上线
- 采用
- 验收
- 覆盖范围
- 交付物
- 决策影响
- 外部认可

### 5.2 数字必须绑定动作

弱：

> Q3 GMV +50%。

如果不能说明用户的动作与数字之间的关系，这个数字没有证明力。

优先形成：

```text
动作 → 中间影响 → 结果
```

若只能证明“参与”，用：`支持 / 推动 / 参与实现 / 在项目周期内达到`，不要把相关性写成因果。

## 6. 模块写作规范

### 6.1 基本信息

默认：

- 姓名
- 电话
- 邮箱
- 单一目标岗位
- 必要时：城市、到岗时间、GitHub/作品集

默认删除：详细地址、婚姻、身份证号、身高体重、星座血型等无关信息。

照片、政治面貌、户籍等仅在目标场景明确需要时保留。

### 6.2 教育背景

推荐：

```text
学校 | 学位/专业 | 时间
GPA/排名（有优势时） | 重要荣誉（可选）
```

规则：

- 通常倒序。
- GPA/排名有优势才突出；不占优可省略，不得改造为虚假优势。
- 主修课程默认不写；仅在应届、经历薄且与岗位强相关时保留 3–5 门。
- 有强实习/项目后，优先给经历腾空间。

### 6.3 Summary / 自我评价

**默认非必需。**

只有能用 2–4 行建立岗位定位和事实证据时保留。

推荐：

```text
[身份/年限/领域] + [2–3 个核心能力] + [代表性场景/结果]
```

禁止无证据空话：

`学习能力强 / 吃苦耐劳 / 性格开朗 / 责任心强 / 团队协作好`

### 6.4 工作 / 实习经历

推荐格式：

```text
公司/团队 | 岗位 | 时间
可选：一句话业务背景
• 2–4 个高价值 bullet
```

优先展示：

- 对口场景
- 个人职责
- 关键判断/动作
- 结果/规模/交付

不是岗位说明书。

### 6.5 项目经历

项目必须回答：

1. 为什么做？
2. 解决什么问题？
3. 你具体负责什么？
4. 为什么选这个方案？
5. 遇到什么难点/取舍？
6. 最终结果是什么？
7. 有无可验证产物？

优先 1–3 个高相关项目，少而精。

避免：功能流水账、技术栈堆砌、教程项目冒充原创、课程作业包装成商业系统。

### 6.6 科研经历

写：

```text
研究问题 → 方法 → 个人贡献 → 结果/产出
```

企业求职只保留对目标岗位有价值的科研信息；学术/复试场景再展开研究基础与潜力。

### 6.7 校园经历

适合：

- 应届无对口实习
- 国企/央企/综合岗
- 经历能证明组织、运营、推进、沟通等能力

仍需写成：

```text
职责范围 → 动作 → 规模/结果
```

不要只写“通知、协助、对接”。

### 6.8 技能与证书

作用：关键词索引 + 补充证据。

可分类：

```text
语言能力：
编程/数据：
产品/设计：
专业工具：
资格证书：
```

技能最好在经历中出现真实使用证据。

弱：`熟练使用 SQL/Python`

强（仅在真实时）：`SQL：窗口函数、留存/复购/TopN；Python：Pandas 数据清洗与分析`

## 7. 分岗位适配

### 7.1 技术 / 后端 / 软件工程

强调：

```text
真实问题 → 工程方案 → 机制/取舍 → 性能/稳定性/规模/上线
```

优先：生产场景、性能、稳定性、部署、测试、排障、工程取舍、开源/作品。

避免：只列 Spring Boot/Redis/Kafka 等技术栈；只写 CRUD/页面；项目无“为什么”。

### 7.2 AI / Agent / LLM

比“框架熟练”更重要：

- 真实场景
- 完整工程链路
- 模型能力边界理解
- 评测与迭代
- 后端/服务化
- 开源/真实使用

**Agent 项目应能回答：**

```text
为什么需要 Agent？
输入/输出是什么？
关键模块是什么？
模型和工具如何调用？
如何兜底？
如何评估？
个人贡献是什么？
```

**RAG 应能回答：**

```text
为什么检索？
知识如何入库/分块/结构化？
如何召回/重排？
如何评估召回与答案质量？
如何更新和保证稳定性？
```

避免只写：`基于 LangChain + RAG + 向量数据库搭建智能问答系统。`

**大模型微调应重点写：**

```text
业务目标
→ 数据来源与问题
→ 标注/生成/清洗/采样
→ 训练方案为什么这样选
→ 评测与误差分析
→ 迭代
→ 结果
```

不要把“在平台上完成 LoRA 微调”本身当核心亮点。

### 7.3 数据分析 / 商业分析

不要把核心价值写成：取数、日报、周报、看板、写 SQL。

应写：

```text
业务问题
→ 指标体系/口径
→ 分析方法
→ 异动归因/分层/漏斗/实验
→ 业务判断
→ 推动动作
→ 结果
```

SQL 最好写进经历，体现具体业务能力，如留存、复购、TopN、窗口函数等（必须真实）。

### 7.4 运营 / 产品 / AI 产品

核心：

```text
用户/业务问题 → 分析判断 → 策略/产品动作 → 协同推进 → 数据结果
```

把“上架、发帖、开会、活动执行”升级为真实的策略、用户、漏斗、渠道、需求、实验、版本迭代等能力证据。

AI 产品还应体现：模型边界、prompt/workflow/agent 设计、测试评测、用户反馈与迭代。

### 7.5 国企 / 央企

相较私企技术岗，可更多强调：

- 需求对接
- 工程落地
- 跨部门协作
- 项目推进
- 测试验收
- 汇报/文档
- 团队组织
- 可量化交付

减少只有技术专家才能理解的细节。校园经历在综合岗可能有更高价值。

### 7.6 应届 / 无实习

可挖掘：

`课程项目 / 大创 / 科研 / 比赛 / 开源 / 个人 Demo / 自媒体 / 社群 / 校园组织 / 志愿项目`

目标不是吹大，而是证明：

```text
对方向有真实投入 + 能独立完成事情 + 有明确方法/学习路径
```

### 7.7 转行

```text
旧经历 → 提取可迁移能力 → 用目标岗位语言表达 → 用新项目/作品补方向证据
```

“想转行”不是证据；实践、作品、项目才是。

### 7.8 学历不占优

- 学历事实必须准确，不虚构不误导。
- 企业求职可把强岗位证据放在更显眼位置，教育背景保持简洁。
- 不主动放大弱项。
- 用对口实习、项目、作品、开源提高第一屏信号密度。

### 7.9 研究生复试 / 学术简历

这是独立路由。更关注：

- 成绩/专业基础
- 英语与文献阅读
- 科研/竞赛中的具体贡献
- 研究兴趣与潜力
- 长期投入能力

课程论文、文献调研可以写，但必须准确标注性质，不得包装成正式科研成果。

## 8. 弱经历的提炼

### 8.1 流水账 → 价值链

原句：

> 负责日常运营工作，协助团队完成活动。

先追问/提取：

```text
对象是谁？
规模多大？
什么问题？
你做了什么判断？
具体动作是什么？
产出/结果是什么？
```

### 8.2 边角料资产化

以下真实小成果可以形成“长期投入”信号：

- 内部分享/技术周刊
- 社区回答
- 小比赛
- issue/PR
- 校内项目
- 作品被采用
- 公开 Demo
- 小规模真实用户

多个中等信号叠加可以增强叙事，但不得把中等成果伪装成顶级成果。

### 8.3 教程/培训项目

可以写，但必须体现自己的部分：

- 自己增加的需求
- 自己的设计/判断
- 遇到的问题
- 为什么修改方案
- 是否部署/真实使用
- 是否有 GitHub/Demo

纯照教程复现不得写成原创项目。

## 9. 语言与风格

### 9.1 说人话

警惕空泛黑话：

`聚焦 / 赋能 / 整合资源 / 深度参与 / 全面提升 / 有效促进 / 持续优化 / 构建闭环`

只有后面跟具体对象、动作、机制和结果时才保留。

### 9.2 一条 bullet 一个主价值

每条尽量做到：责任清楚、动作清楚、结果清楚、关键词自然。

不要把 4–5 件事用顿号塞进一个长句。

### 9.3 去 AI 味

改写后检查：

- 是否所有句子都用同一模板；
- 是否大量“通过……实现……”；
- 是否过度正式、夸张；
- 是否把实习生写得像高管；
- 是否概念密度远高于事实密度。

简历应专业，但要像真实的人做过真实工作。

## 10. 排版与可扫描性

### 10.1 篇幅

- 应届/初级：1 页优先。
- 高质量经验较多：可 2 页。
- 不要为了“一页”删核心成果，也不要用极小字号硬压。

### 10.2 默认视觉规范

- 白底、黑/深灰正文
- 最多一个强调色
- 1–2 种字体
- 上下结构优先
- 对齐清楚、适当留白
- 日期、标点、大小写统一
- 模块标题明确

避免复杂图标、多色装饰、花哨模板、难读分栏。

### 10.3 第一屏

应尽快出现：

- 目标岗位
- 最相关实习/项目
- 2–3 个强能力信号
- 必要的可验证链接

不要让无关课程、兴趣、普通证书占据黄金位置。

### 10.4 在线简历与附件

如果同时生成招聘平台在线简历和 PDF：

- 公司、岗位、时间、职责、结果必须一致；
- 可按平台字数压缩，但不得改事实；
- 在线简历不能明显弱于附件。

## 11. 高频失败模式

发现以下问题应主动修复：

1. **流水账**：只有“负责/参与/协助”，没有价值。
2. **岗位说明书**：删掉公司名后可放进任何同行 JD。
3. **空洞自评**：认真、负责、学习能力强但无证据。
4. **教育堆料**：课程/低优势 GPA 挤掉核心经历。
5. **数字装饰**：数字与个人动作无关系。
6. **AI/黑话腔**：听起来高级，但说不清做了什么。
7. **项目目的不成立**：解释不了为什么做、为什么用该方案。
8. **关键词堆叠**：技术名词很多，但无使用证据。
9. **过度包装**：实习生像 COO、团队成果写成个人主导。
10. **通用简历**：一个版本投所有方向。
11. **无关填充**：与岗位无关的证书、兼职、校园事务占空间。
12. **附件不一致**：在线简历与 PDF 的事实对不上。

## 12. 冲突规则统一

| 争议 | 默认规则 | 例外 |
|---|---|---|
| 必须一页？ | 应届/初级 1 页优先 | 高价值经验较多可 2 页 |
| 自我评价要不要？ | 默认可删 | 能用事实快速定位时保留 |
| 主修课程要不要？ | 默认不写 | 应届、经历薄且强相关时少量保留 |
| 每条都要数字？ | 有可信数字优先 | 无数字可写上线、采用、交付、规模、决策 |
| 严格按时间？ | 模块内倒序 | 整体可按相关性前置，不伪造时间 |
| 技术细节写多少？ | 写到能证明能力 | 技术岗更深，央国企综合岗更浅 |
| 学历弱项怎么处理？ | 准确、简洁、不放大 | 复试/学术场景需更完整 |
| 照片是否需要？ | 非写作核心，默认不主动添加 | 单位/地区/用户明确要求时 |

## 13. 输出规范

### 13.1 用户要求“直接改”

优先输出可直接粘贴的最终简历内容。

如需说明：

```text
1. 修改后版本
2. 关键修改（简短）
3. 仍需补充的事实/数字
```

### 13.2 用户要求“锐评”

按严重度：

```text
P0：真实性/定位/筛选致命问题
P1：匹配度、证据、结果明显不足
P2：语言、顺序、排版优化
```

每个问题给：

```text
问题 → 为什么影响筛选 → 怎么改 → 改写示例
```

### 13.3 用户要求“针对 JD 优化”

内部先完成 JD—证据映射。

用户可见输出默认：

```text
A. 优化后的简历
B. 无法凭空补齐的 JD 缺口（如有）
```

除非用户要求分析过程，否则不要输出冗长方法论。

## 14. 最终自检

### 定位
- [ ] 一个主目标岗位
- [ ] 第一屏有 2–3 个强匹配信号
- [ ] 不是“一份通投所有岗位”的简历

### 内容
- [ ] 核心经历靠前
- [ ] 每段能看出个人职责
- [ ] bullet 不只是“负责/参与”
- [ ] 有结果、规模、交付或可验证产物
- [ ] 数字与动作有合理关系
- [ ] 无关信息已删/压缩

### JD
- [ ] 关键硬技能有真实证据
- [ ] 重要关键词自然出现
- [ ] 未为了过 ATS 写不会的技能

### 真实性
- [ ] 无编造经历
- [ ] 无夸大 ownership
- [ ] 无虚构数据
- [ ] 团队成果未冒充个人成果
- [ ] 写入的技术都能解释
- [ ] 重点内容可在面试展开

### 语言/版式
- [ ] 无空洞自评
- [ ] 无黑话堆砌
- [ ] 无明显 AI 腔
- [ ] 每条 bullet 只有一个主价值
- [ ] 专有名词、日期、格式统一
- [ ] 篇幅与资历匹配

## 15. 内部评分 Rubric（100）

| 维度 | 分值 |
|---|---:|
| 岗位匹配度 | 25 |
| 证据强度 | 20 |
| 结果与影响 | 20 |
| 个人贡献清晰度 | 15 |
| 可信度 | 10 |
| 可扫描性 | 5 |
| 语言质量 | 5 |

解释：

```text
90–100：可定稿
80–89：较强，局部强化
70–79：匹配/结果/证据至少一项明显不足
<70：不要继续润色，应回到定位和经历挖掘
```

## 16. 可复用模板

### 通用

```text
• [任务标签]：在 [场景] 下，针对 [问题]，负责 [个人范围]；通过 [方法/判断] 完成 [动作]，最终 [结果/影响/产物]。
```

### 技术

```text
• [工程问题]：针对 [性能/稳定性/可扩展性问题]，设计并实现 [方案]，通过 [关键机制] 优化 [指标]，最终 [上线/性能/稳定性结果]。
```

### 数据分析

```text
• [分析主题]：围绕 [业务问题] 搭建/拆解 [指标]，使用 [SQL/Python/统计方法] 定位 [关键原因]，推动 [业务动作]，最终 [结果]。
```

### AI / Agent

```text
• [场景]：面向 [真实用户/业务问题] 设计 [Agent/LLM 系统]，负责 [个人模块]；通过 [workflow/tool/retrieval/evaluation/backend mechanism] 解决 [难点]，最终 [评测/使用/上线/开源结果]。
```

### 运营 / 产品

```text
• [策略主题]：基于 [用户/业务数据] 识别 [问题/机会]，制定并推进 [策略/产品动作]，协同 [相关团队] 完成落地，使 [关键结果] 发生 [变化]。
```

### 科研

```text
• 围绕 [研究问题]，负责 [个人研究任务]，采用 [方法] 完成 [关键分析/实验]，得到 [研究发现/指标/论文/报告/数据集]。
```

## 17. 一句话原则

> **不要只润色用户写了什么；先判断这件事是否值得写，再把真实证据写成目标岗位最容易理解的形式。**
